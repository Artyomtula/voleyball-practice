# Как устроен проект: объяснение для подготовки к защите

Этот документ объясняет проект с нуля: что он делает, из каких частей состоит, как работает
нейросетевая часть и алгоритм, какие получились результаты и что отвечать на вопросы.
Все цифры взяты из реальных запусков (файлы лежат в `examples/experiment/`).

## Коротко

Пользователь загружает запись волейбольного матча через веб-страницу. Сервер ставит видео
в очередь, фоновый процесс (воркер) прогоняет каждый кадр через две нейросети: одна ищет мяч,
другая людей. Из полученных координат простой алгоритм решает, идёт ли в кадре игра (`GAME`)
или пауза (`NON_GAME`), и склеивает игровые кадры в интервалы-розыгрыши. Розыгрыши сохраняются
в базу и показываются пользователю списком «Rally 1: 00:20.7 → 00:29.0».

---

## 1. Какую проблему решает приложение

Запись матча длится 1,5–2 часа, а мяч в игре примерно треть этого времени. Остальное — паузы
между розыгрышами, тайм-ауты, замены. Тренеру и игрокам нужны именно розыгрыши: чтобы
посмотреть только игру, нарезать клипы, считать статистику. Вручную отмечать начало и конец
каждого из 150–200 розыгрышей долго. Приложение делает эту разметку автоматически.

В задании ИР 4 минимальный уровень сформулирован так: разделить видео на игровые и неигровые
моменты. Подачу, приём, атаку и блок распознавать не нужно, это следующие этапы.

## 2. Как устроена архитектура

Схема: `docs/architecture.png`. Пять частей:

| Часть | Технология | Роль |
|---|---|---|
| Интерфейс | React (сборщик Vite) | поле загрузки видео и вывод найденных розыгрышей |
| API | FastAPI | принимает HTTP-запросы, работает с базой, ставит задачи в очередь |
| База данных | SQLite через SQLAlchemy | пользователи, видео, задания, розыгрыши |
| Очередь | Redis | хранит задачи, пока воркер их не заберёт |
| Воркер | Celery | выполняет долгую обработку видео нейросетями |

Всё запускается одной командой `docker compose up --build`: Docker Compose поднимает четыре
контейнера (`redis`, `api`, `worker`, `frontend`). API и воркер собраны из одного образа и
используют общий том `app-data`, где лежат база `app.db`, загруженные видео и JSON-файлы
с детекциями.

## 3. Для чего нужен каждый компонент

- React рисует одну страницу: поле загрузки видео, ход обработки и результат. Без него пришлось бы
  работать с API через curl или Swagger.
- FastAPI — веб-фреймворк на Python. Он описывает эндпоинты, сам проверяет входные данные
  по схемам Pydantic и генерирует документацию Swagger (`http://localhost:8000/docs`).
- SQLite — база в одном файле, не нужен отдельный сервер. Для учебного проекта с одним
  пользователем этого достаточно.
- Redis — быстрое хранилище «ключ-значение» в памяти. Здесь он работает брокером:
  API кладёт в него сообщение «обработать задание №5», воркер его забирает.
- Celery — библиотека фоновых задач. Без неё обработка 8-минутного видео (около 8 минут
  на процессоре) шла бы прямо внутри HTTP-запроса, и браузер получил бы ошибку по тайм-ауту.
- Docker Compose описывает все контейнеры в одном файле, чтобы проект запускался одинаково
  на любом компьютере.

## 4. Как связаны React, FastAPI, SQLite, Redis и Celery

Путь одного видео:

1. React отправляет `POST /api/videos` с файлом. Запрос идёт на сервер Vite, а тот проксирует
   всё, что начинается с `/api`, в контейнер `api`.
2. FastAPI сохраняет файл в `/data/uploads/` под случайным именем, читает через OpenCV FPS,
   размер кадра и длительность и создаёт строку в таблице `videos` со статусом `uploaded`.
3. Сразу после загрузки страница отправляет `POST /api/videos/{id}/process`. API создаёт
   строку в `processing_jobs` (статус `queued`) и вызывает `process_video.delay(job_id)`.
   Вызов `delay` не выполняет функцию, а кладёт в Redis сообщение с её именем и аргументом.
4. Воркер Celery постоянно слушает Redis. Он получает сообщение и вызывает `process_video(job_id)`.
5. Воркер читает видео, запускает нейросети, после каждых 9 кадров пишет в базу процент
   выполнения, в конце сохраняет JSON с детекциями и розыгрыши, ставит статус `completed`.
6. React раз в 2 секунды спрашивает `GET /api/videos/{id}/job` и показывает процент.
   Когда статус стал `completed`, он запрашивает `GET /api/videos/{id}/rallies` и выводит
   таблицу розыгрышей и JSON.

API и воркер не общаются напрямую: API пишет задачу в Redis, а результат воркер пишет в SQLite.

## 5. Зачем используется SQLAlchemy

SQLAlchemy — ORM: она связывает таблицы базы с классами Python. Вместо SQL-запроса
`INSERT INTO videos (...) VALUES (...)` пишется `db.add(Video(...))`, вместо `SELECT` —
`db.get(Video, video_id)`. Плюсы:

- код работает с объектами и их связями (`video.rallies`, `job.video`);
- SQLAlchemy сама подставляет параметры в запросы, поэтому SQL-инъекции исключены;
- по описанию моделей Alembic автоматически строит миграции;
- для перехода с SQLite на PostgreSQL достаточно поменять строку подключения `DATABASE_URL`.

Модели описаны в `backend/app/models.py` в стиле SQLAlchemy 2.0 (`Mapped`, `mapped_column`).

## 6. Для чего нужны миграции Alembic

Миграция — это файл с инструкциями, как изменить схему базы: создать таблицу, добавить
колонку, индекс. Миграции хранятся в `backend/alembic/versions/` и применяются по порядку
командой `alembic upgrade head`. Зачем это нужно:

- схема базы хранится в Git вместе с кодом, её историю видно;
- на любом компьютере база создаётся одинаково (Docker-контейнер `api` выполняет
  `alembic upgrade head` при каждом старте);
- при изменении моделей не нужно удалять базу с данными, достаточно новой миграции.

У нас одна миграция `0001_initial_tables.py`, она создаёт все четыре таблицы. Её сгенерировала
команда `alembic revision --autogenerate`, потом её вручную привели к читаемому виду. Проверка
`alembic check` подтверждает, что миграция совпадает с моделями. Для SQLite в `env.py`
включён `render_as_batch=True`: SQLite почти не умеет `ALTER TABLE`, и Alembic при будущих
изменениях будет пересоздавать таблицу целиком.

## 7. Какие таблицы есть в базе и почему

ER-диаграмма: `docs/er-diagram.png`.

- `users` — пользователи: `email` (уникальный), `password_hash`, `created_at`. Таблицу требует
  задание ИР 1. Регистрация и вход — это задание ИР 2, поэтому в нашей системе таблица пока
  пустая; пароль в ней будет храниться только в виде хеша.
- `videos` — загруженные видео: владелец `user_id` (пока пустой, его заполнит вход из ИР 2),
  исходное имя `filename`, путь на диске
  `file_path`, метаданные `duration`, `fps`, `width`, `height` и `status`.
- `processing_jobs` — запуски обработки. Видео можно обработать несколько раз, и у каждого
  запуска своя строка: `status`, `progress` (0–100), `started_at`, `finished_at`, путь к JSON
  с детекциями `detections_path`, текст ошибки `error_message`.
- `rallies` — найденные розыгрыши: порядковый `number`, время начала и конца в секундах и
  в кадрах, `serve_side`.

Связи «один ко многим»: пользователь → видео, видео → задания, видео → розыгрыши.

Почему задания вынесены в отдельную таблицу, а не в поля видео: у видео может быть несколько
запусков (например, после изменения параметров), и история запусков с ошибками сохраняется.

Целостность проверяет сама база: внешние ключи (`ON DELETE CASCADE` — удалили видео, удалились
его розыгрыши), `CHECK` на список статусов, `UNIQUE(video_id, number)` (у одного видео не может
быть двух розыгрышей с одним номером). В SQLite внешние ключи по умолчанию выключены, поэтому
в `database.py` при каждом подключении выполняется `PRAGMA foreign_keys=ON`.

Три поля добавлены сверх задания, у каждого есть причина: `file_path` (где лежит файл),
`detections_path` (где лежат детекции) и `error_message` (что пошло не так).

`serve_side` всегда `unknown`: сторону подачи определяет бонусная часть задания ИР 5,
поле заложено в схему заранее.

## 8. Почему выбран такой способ хранения детекций

Детекция — это одна найденная нейросетью рамка или точка в одном кадре. Их очень много.
На нашем 8-минутном фрагменте получилось 123 690 детекций (мяч + люди). Сравнивали три варианта:

1. Все детекции в SQLite. Измерено: таблица заняла 9,4 МБ. На двухчасовой матч это примерно
   1,9 млн строк и 140 МБ. SQLite разрешает только одного пишущего, и пока воркер вставляет
   миллионы строк, API ждёт. Зато детекции удобно выбирать SQL-запросами.
2. JSON или CSV на диске + путь в базе. Тот же фрагмент — файл 5,5 МБ. База остаётся маленькой,
   а детекции можно перечитать и пересчитать розыгрыши с другими параметрами без нейросетей.
3. Только итоговые розыгрыши в базе. Минимум места, но детекции теряются. Чтобы попробовать
   другие параметры алгоритма, придётся заново гонять нейросети (8 минут на 8 минут видео).

Выбран комбинированный вариант: розыгрыши (то, что нужно интерфейсу) в SQLite, детекции в JSON,
путь к файлу в `processing_jobs.detections_path`. Интерфейсу отдельные детекции не нужны, а
сохранённый JSON позволил в этой работе за секунды перебрать десятки наборов параметров.

## 9. Что такое YOLO и как она обнаруживает объекты

YOLO (You Only Look Once) — семейство нейросетей для обнаружения объектов. Модель за один
проход по изображению выдаёт список рамок: координаты прямоугольника, класс объекта и
уверенность от 0 до 1.

Упрощённо это работает так:

1. Изображение уменьшается до размера входа (по умолчанию 640 пикселей по длинной стороне).
2. Свёрточная сеть («backbone») превращает картинку в карты признаков: сначала простые
   (края, пятна), потом сложные (силуэт человека, мяч).
3. «Голова» сети для каждого участка карты признаков предсказывает, есть ли там объект,
   какого он класса и где точно его границы.
4. Лишние пересекающиеся рамки одного объекта убираются. Обычно это делает алгоритм NMS;
   у YOLO26 есть режим без NMS (end-to-end), но по умолчанию Ultralytics использует NMS.

Мы берём готовую модель `yolo26n.pt` (n — самая маленькая и быстрая версия), обученную
на наборе COCO из 80 классов. Нам нужен только класс 0 — «person»:

```python
results = self.model.predict(frames, classes=[PERSON_CLASS], conf=self.confidence, verbose=False)
```

`classes=[0]` — искать только людей, `conf=0.3` — отбрасывать рамки с уверенностью ниже 0,3.

В COCO есть и класс 32 «sports ball». Мы проверили, может ли YOLO26 сама находить волейбольный
мяч (скрипт `scripts/compare_ball_models.py`): на роликах со статичной камерой она нашла мяч
только в 0–1 % кадров при стандартном размере входа 640 и в 15–18 % при 1280. Мяч в таком кадре
занимает 10–15 пикселей, часто размыт движением, а при уменьшении до 640 пикселей становится
почти точкой. Поэтому YOLO26 у нас ищет только игроков. Список игроков нужен во временном
ряду: задание ИР 4 требует поле `players[]`. Алгоритм выделения розыгрышей его не использует.

## 10. Для чего используется fast-volleyball-tracking

[fast-volleyball-tracking-inference](https://github.com/asigatchov/fast-volleyball-tracking-inference) —
открытый репозиторий (лицензия MIT) с моделями, обученными специально находить волейбольный мяч.
Модели называются VballNet и устроены по идее TrackNet: на вход получают не один кадр,
а 9 кадров подряд, и видят движение. Маленький размытый мяч на одном кадре похож на пятно,
а на последовательности кадров виден как точка, которая летит по дуге.

Мы взяли модель `VballNetV4c` в формате ONNX (около 1 МБ) и запускаем её через
ONNX Runtime. Сам репозиторий как библиотеку не подключаем: в нём нет пакета для импорта,
только скрипты. Предобработку и разбор выхода мы повторили по скрипту автора
`src/inference_onnx_seq_gray_v2.py`.

На трёх роликах с эталонной разметкой мяча VballNetV4c получила F1 0,79–0,85, а YOLO26n
с классом «sports ball» — не больше 0,30 (таблица в `examples/experiment/ball_models.md`).

Поэтому в проекте VballNet ищет мяч, а YOLO26 — людей в кадре.

## 11. Как программа получает координаты мяча

Код в `backend/app/detection.py`. Последовательность:

1. OpenCV читает видео пакетами по 9 кадров (`read_frames`).
2. Каждый кадр переводится в оттенки серого, уменьшается до 512×288 и делится на 255,
   чтобы яркость была от 0 до 1 (`preprocess`).
3. 9 кадров складываются в массив формы `(1, 9, 288, 512)` и подаются в модель.
4. Модель возвращает 9 «тепловых карт» размером 288×512 — по одной на кадр. Значение в каждой
   точке ≈ вероятность, что там мяч.
5. Для каждой карты (`find_ball`): оставляем точки со значением больше 0,5, находим связные
   области, берём самую большую, её центр и есть мяч. Уверенность — максимум карты в этой области.
6. Координаты переводятся обратно в размер исходного кадра: x умножается на `ширина / 512`,
   y — на `высота / 288`.

Если ни одна точка не превышает 0,5, мяч в кадре не найден: `ball_x` и `ball_y` равны `None`.
Последний пакет может быть короче 9 кадров, тогда он дополняется копиями последнего кадра,
а лишние результаты отбрасываются.

В итоге для каждого кадра получается запись временного ряда, как требует задание:

```json
{"frame": 100, "ball_x": 1554.1, "ball_y": 591.4, "ball_confidence": 0.566,
 "players": [[1188.1, 567.2, 1274.4, 790.0, 0.844], [939.8, 551.4, 1026.3, 787.3, 0.787]]}
```

Каждый игрок — рамка `[x1, y1, x2, y2, уверенность]` в пикселях.

## 12. Как рассчитывается перемещение мяча

Скорость мяча в кадре i считается по предыдущему кадру j, где мяч тоже был найден:

```
v_i = sqrt((x_i - x_j)^2 + (y_i - y_j)^2) / W / ((i - j) / fps)
```

- числитель — расстояние в пикселях между двумя положениями мяча;
- деление на ширину кадра `W` делает скорость независимой от разрешения видео:
  0,1 значит «за секунду мяч сместился на 10 % ширины кадра»;
- `(i - j) / fps` — сколько секунд прошло между кадрами.

Если предыдущее положение было слишком давно (больше `max_gap` = 1 с назад), скорость не считается:
мяч мог за это время улететь куда угодно, и такое «перемещение» ничего не значит.

Пример: при 30 кадрах в секунду и ширине 1920 мяч сместился за один кадр на 30 пикселей.
`v = 30 / 1920 / (1 / 30) ≈ 0,47` ширины кадра в секунду, это летящий мяч.

## 13. Как определяется состояние GAME / NON_GAME

Сначала каждый кадр получает «сырую» отметку, активный он или нет (`active_frames`). Кадр активный,
если выполнены два условия:

1. мяч найден (`ball_x` не `None`);
2. мяч движется: `v ≥ min_speed` (0,1 ширины кадра в секунду).

Почему именно эти признаки:

- *Наличие мяча* — главный признак: в розыгрыше мяч в кадре почти всегда.
- *Скорость* отсекает мяч в руках подающего, лежащий на полу или запасной мяч у скамейки.
  Мяч в игре летит со скоростью 5–30 м/с, а площадка шириной 9 м занимает заметную часть кадра,
  так что даже медленный мяч в игре движется быстрее 0,1 ширины кадра в секунду.

Число людей в кадре алгоритм не использует. Список игроков `players[]` сохраняется во временном
ряду, потому что его требует задание, но в правило не входит: правило оставлено минимальным.

Сырая отметка шумная: мяч теряется на долю секунды, бывают ложные срабатывания. На фрагменте
трансляции мяч найден только в 35 % кадров розыгрышей и в 19 % кадров пауз. Поэтому окончательное
состояние `GAME`/`NON_GAME` получается после временной фильтрации.

## 14. Зачем нужна временная фильтрация

Нейросеть ошибается от кадра к кадру. В розыгрыше мяч может пропасть на 5–10 кадров
(закрыт игроком, размыт, вылетел за верх кадра), и без фильтрации один розыгрыш развалился бы
на десяток кусочков. В паузе нейросеть иногда на секунду «находит» мяч там, где его нет, и
без фильтрации появились бы ложные розыгрыши. Фильтрация исправляет эти ошибки, опираясь на
то, что игра и пауза длятся секунды, а не отдельные кадры.

Шаги (`classify_frames` и `find_rallies` в `backend/app/rallies.py`):

1. **Заполнение пропусков** (`fill_gaps`). Если между двумя активными кадрами не больше
   `max_gap` = 1 с неактивных, они тоже считаются игрой.
2. **Удаление коротких фрагментов.** Непрерывные куски игры короче `min_duration` = 2 с
   становятся `NON_GAME`: настоящий розыгрыш (подброс, подача, полёт мяча) не бывает короче.
   После этого шага у каждого кадра есть итоговая метка `GAME` или `NON_GAME`.
3. **Объединение сегментов** (`merge_segments`). Если пауза между двумя игровыми сегментами не больше
   `merge_gap` = 2 с, они склеиваются в один розыгрыш. Это спасает розыгрыш, в котором мяч
   надолго улетел из кадра.

Порядок шагов важен. Мы проверили обратный порядок (сначала объединение, потом удаление коротких):
F1 упал с 0,609 до 0,542. Если сначала объединять, короткий ложный фрагмент рядом с настоящим
розыгрышем успевает к нему «приклеиться», и границы розыгрыша уезжают.

## 15. Как формируются интервалы Rally

Каждый итоговый сегмент `(первый кадр, последний кадр)` превращается в розыгрыш:

```python
{"number": 1, "start": round(start / fps, 2), "end": round(end / fps, 2),
 "start_frame": start, "end_frame": end, "serve_side": "unknown"}
```

Пример при 10 кадрах в секунду. Мяч летит в кадрах 10–30, пропадает на 5 кадров
(31–35) и снова летит в кадрах 36–60.

1. Активные кадры: 11–30 и 36–60. Кадр 10 неактивный: это первое появление мяча, скорость
   по нему посчитать не по чему.
2. Пропуск 31–35 длится 5 кадров (0,5 с), это не больше `max_gap` (10 кадров), заполняем → 11–60.
3. Длина 50 кадров = 5 с, это не меньше `min_duration`, оставляем.
4. Других сегментов нет, объединять нечего.
5. Результат: `{"number": 1, "start": 1.1, "end": 6.0, "start_frame": 11, "end_frame": 60}`.

Розыгрыши записываются в таблицу `rallies`, а API отдаёт их в JSON того вида, что в задании:
`{"video_id": 1, "rallies": [{"start": 1.1, "end": 6.0, ...}]}`.

## 16. Как выбирались параметры алгоритма

Сначала значения выбирались из устройства волейбола, затем проверялись на размеченном видео:

| Параметр | Значение | Почему |
|---|---|---|
| `min_speed` | 0,1 ширины кадра/с | мяч в игре летит 5–30 м/с, в руках или на полу — меньше 1 м/с |
| `max_gap` | 1 с | мяч закрыт игроком или вылетел за кадр обычно на доли секунды |
| `min_duration` | 2 с | подброс, подача и полёт мяча вместе занимают не меньше 2 с |
| `merge_gap` | 2 с | паузы между настоящими розыгрышами — от 8–10 с, склейка до 2 с их не сливает |

Проверка шла на фрагменте телетрансляции матча TEVA GRC – Calcit Kamnik (7 мин 56 с, лицензия
CC BY 3.0). В нём вручную размечены 16 розыгрышей (`examples/ground_truth/teva_kamnik_2012_part.json`),
затем по одному менялся каждый параметр, остальные оставались по умолчанию (`scripts/evaluate.py --sweep`,
график `docs/experiment_parameters.png`). Что получилось:

- `max_gap` влияет сильнее всего. При 0,2 с почти ничего не находится (F1 0,03): мяч на
  трансляции теряется постоянно. При 1 с F1 максимальный, 0,609. Дальше растёт полнота, но
  розыгрыши склеиваются с паузами, и точность падает (при 3 с F1 0,48).
- `min_duration`: 0,5 с → 39 найденных интервалов, много мусора; 2 с → 31; 3 с → 22 и F1 0,64;
  5 с → 13 интервалов и F1 0,67, но совпадают уже 11 розыгрышей из 16, а полнота падает до 0,58.
  Оставлено 2 с, чтобы не терять короткие розыгрыши: самый короткий в эталоне длится 4,5 с,
  а найденный кусок розыгрыша бывает ещё короче.
- `merge_gap` почти не влияет на F1 (0,57–0,61), но меняет число найденных интервалов
  с 41 (без склейки) до 16 (склейка до 8 с).
- `min_speed` влияет слабо (F1 0,59–0,61): на трансляции мяч в паузах чаще не находится вовсе,
  чем лежит неподвижно.

## 17. Какие проблемы возникают при анализе видео

- **Ракурс и качество.** VballNet обучена на статичной камере за лицевой линией. На телетрансляции
  (другие камеры, 480p, сжатие) мяч нашёлся только в 35 % кадров розыгрышей.
- **Монтаж трансляции.** Смена камер, крупные планы, повторы. Алгоритм их от игры не отличает:
  из 14 лишних интервалов в семи YOLO26 находит в кадре от одного до четырёх человек (медиана
  по кадрам интервала), то есть показан крупный план.
- **Мяч не в игре, но движется.** Подающий стучит мячом об пол, игроки перебрасывают мяч после
  розыгрыша. Отсюда ранние начала розыгрышей: в среднем начало найдено на 2,7 с раньше или позже
  эталона, конец точнее (1,2 с).
- **Несколько мячей** на разминке или у скамейки запасных.
- **Окклюзии и размытие**: мяч закрыт игроком или смазан на кадре.
- **Скорость обработки.** На процессоре 8 минут видео обрабатываются примерно за 8 минут,
  основное время уходит на YOLO26. В Docker Desktop на macOS нейросети работают в 2,5–3 раза медленнее:
  ролик длительностью 33 с там обрабатывался 5 мин 48 с вместо 49 с.

## 18. Как проверить качество результата

1. **Эталон.** Человек просматривает видео и записывает начало и конец каждого розыгрыша.
   Наш эталон — 16 розыгрышей, просмотр с шагом 0,5 с, погрешность границ около 1 с.
2. **Покадровые метрики.** Каждый кадр — `GAME` или `NON_GAME` по эталону и по алгоритму:
   - точность (precision) — какая доля кадров, отмеченных алгоритмом как игра, действительно игра;
   - полнота (recall) — какую долю настоящих игровых кадров алгоритм нашёл;
   - F1 — среднее гармоническое точности и полноты.
3. **Метрики по розыгрышам.** Найденный интервал совпал с эталонным, если IoU (длина пересечения,
   делённая на длину объединения) не меньше 0,5. Считаем число совпавших и среднюю ошибку
   начала и конца в секундах.

Результат с параметрами по умолчанию: найден 31 интервал, 13 из 16 розыгрышей совпали,
точность 0,51, полнота 0,76, F1 0,61, ошибка начала 2,7 с, конца 1,2 с.
На трёх роликах со статичной камерой, где по эталонной разметке мяча идёт непрерывная игра,
найдено по одному интервалу: 0,03–32,6 с из 33,1 с (gtu_20250316_002), 0,93–11,11 с из 11,2 с
(gtu_20250316_003) и 0,3–4,77 с из 4,8 с (gtu_20250316_005).

Автотестов в проекте нет: работа проверялась запуском на реальных видео с эталонной разметкой
и сквозным прогоном в Docker через API и браузер.

## 20. Как объяснить работу проекта преподавателю

План рассказа на 5 минут:

1. Задача. В записи матча мяч в игре примерно треть времени; нужно автоматически найти интервалы
   розыгрышей. Минимальный уровень по заданию — `GAME`/`NON_GAME`.
2. Архитектура (показать `docs/architecture.png`). React → FastAPI → SQLite; долгая обработка
   через очередь Redis и воркер Celery; всё в Docker Compose.
3. База (показать `docs/er-diagram.png`). Четыре таблицы, миграция Alembic. Детекции в JSON,
   потому что их миллионы, а интерфейсу нужны только розыгрыши; цифры сравнения.
4. Нейросети. VballNet ищет мяч по 9 кадрам, YOLO26 — людей. Почему не YOLO для мяча:
   F1 0,01–0,28 против 0,82.
5. Алгоритм (показать `docs/algorithm.png`). Активный кадр = мяч найден и летит быстрее порога;
   затем заполнение пропусков, удаление коротких, склейка.
6. Эксперимент (показать `docs/experiment_timeline.png` и `docs/experiment_parameters.png`).
   16 эталонных розыгрышей, 13 найдено, F1 0,61; как влияют параметры.
7. Ограничения и развитие. Модель мяча под статичную камеру; сторона подачи не определяется;
   можно добавить разметку площадки и обучаемый классификатор.

Для живой демонстрации подойдёт короткий ролик `gtu_20250316_005.mp4` (4,8 с): в Docker он обрабатывается
меньше минуты, результат — один розыгрыш 00:00.3 → 00:04.7. Ролик `gtu_20250316_002.mp4` (33 с) нативно
обрабатывается около минуты, в Docker — около 6 минут; результат — один розыгрыш 00:00.0 → 00:32.6.

## 22. Разбор кода: каждый файл и каждая функция

### Как файлы связаны между собой

Браузер (`App.jsx`) отправляет видео в API (`main.py`). API сохраняет файл, пишет строку в базу
(`models.py`, `database.py`) и кладёт задачу в Redis. Воркер (`tasks.py`) забирает задачу, прогоняет
видео через нейросети (`detection.py`), выделяет розыгрыши алгоритмом (`rallies.py`) и пишет их
в базу. Браузер раз в 2 секунды спрашивает API о статусе и в конце получает розыгрыши.
Настройки для всех модулей лежат в `config.py`.

### backend/app/config.py — настройки

Функций нет, только константы. Любое значение можно переопределить переменной окружения
(`os.getenv`): так Docker подставляет свои пути.

- `BASE_DIR` — папка `backend`.
- `DATA_DIR` — где лежат база, видео и результаты; в Docker это `/data`, общий том.
- `UPLOAD_DIR`, `RESULTS_DIR` — подпапки для загруженных видео и JSON с детекциями.
- `DATABASE_URL` — строка подключения к SQLite.
- `REDIS_URL` — адрес Redis для Celery.
- `BALL_MODEL_PATH` — файл модели мяча VballNetV4c (`.onnx`).
- `PLAYER_MODEL` — файл модели людей `yolo26n.pt`.
- `ALLOWED_VIDEO_EXTENSIONS` — расширения, которые принимает загрузка.

### backend/app/database.py — подключение к базе

- `DATA_DIR.mkdir(...)` создаёт папку данных, иначе SQLite не сможет создать файл базы.
- `engine` — подключение к SQLite. Параметр `check_same_thread=False` нужен, потому что FastAPI
  выполняет запросы в разных потоках.
- `SessionLocal` — фабрика сессий. Сессия — это «разговор» с базой: через неё читают и сохраняют объекты.
- `enable_foreign_keys(...)` вызывается при каждом новом подключении (декоратор `@event.listens_for`)
  и выполняет `PRAGMA foreign_keys=ON`. Без этого SQLite не проверяет внешние ключи.
- `Base` — общий родитель всех моделей; по нему SQLAlchemy и Alembic знают список таблиц.
- `get_db()` — генератор для FastAPI: открывает сессию на время одного запроса и закрывает её
  в `finally`, даже если запрос завершился ошибкой.

### backend/app/models.py — таблицы

- `VIDEO_STATUSES`, `JOB_STATUSES`, `SERVE_SIDES` — допустимые значения из задания.
- `allowed_values(column, values)` собирает текст условия `status IN ('uploaded', ...)` для
  ограничения CHECK, чтобы не писать списки вручную.
- `User` — таблица `users`: `id`, `email` (уникальный), `password_hash`, `created_at` (время ставит
  сама база, `server_default=func.now()`). Связь `videos` — список видео пользователя.
- `Video` — таблица `videos`: `user_id` (может быть пустым), `filename` (имя от пользователя),
  `file_path` (где файл на диске), `duration`, `fps`, `width`, `height`, `status` (по умолчанию
  `uploaded`), `created_at`. CHECK не даёт записать неизвестный статус. Связи `jobs` и `rallies`
  с `cascade="all, delete-orphan"`: удаление видео удаляет его задания и розыгрыши.
- `ProcessingJob` — таблица `processing_jobs`: `video_id`, `status`, `progress` (CHECK от 0 до 100),
  `started_at`, `finished_at`, `detections_path`, `error_message`.
- `Rally` — таблица `rallies`: `video_id`, `number`, `start_time`, `end_time`, `start_frame`,
  `end_frame`, `serve_side`. Номер уникален в пределах видео, `serve_side` из списка,
  `end_frame` не меньше `start_frame`.

Запись `Mapped[int | None]` означает, что колонка может быть пустой (NULL), а `Mapped[int]` — обязательная.

### backend/app/schemas.py — формат ответов API

Классы Pydantic описывают поля, которые отдаёт API. FastAPI по ним проверяет ответ, а Swagger
показывает их как документацию. `from_attributes=True` позволяет вернуть объект модели SQLAlchemy
напрямую, без ручного перекладывания полей.

- `VideoOut` — видео: `id`, `filename`, `duration`, `fps`, `width`, `height`, `status`, `created_at`.
- `JobOut` — задание: `id`, `video_id`, `status`, `progress`, `started_at`, `finished_at`, `error_message`.
- `RallyOut` — один розыгрыш: `number`, `start`, `end`, `start_frame`, `end_frame`, `serve_side`.
- `RalliesOut` — ответ со списком розыгрышей: `video_id` и `rallies`.

### backend/app/video_utils.py — метаданные видео

- `read_video_info(path)` открывает файл через OpenCV и читает FPS, число кадров, ширину и высоту;
  длительность равна числу кадров, делённому на FPS. Если файл не открылся или значения нулевые
  (это не видео), возвращает `None`. `capture.release()` в `finally` закрывает файл в любом случае.

### backend/app/main.py — API

- `app = FastAPI(...)` — само веб-приложение.
- `DbSession` — короткая запись «сессия базы из `get_db`»: FastAPI сам открывает сессию для каждого запроса.
- `get_video_or_404(db, video_id)` ищет видео по номеру и, если его нет, отвечает 404. Её
  используют все методы, которые работают с одним видео.
- `health()` — `GET /api/health`, ответ `{"status": "ok"}`: проверка, что сервер работает.
- `upload_video(file, db)` — `POST /api/videos`. Проверяет расширение (иначе 400), сохраняет файл
  в `uploads` под случайным именем `uuid4`, читает метаданные через `read_video_info` (если это не
  видео, удаляет файл и отвечает 400), создаёт строку `Video` и возвращает её с кодом 201.
- `list_videos(db)` — `GET /api/videos`: все видео, новые первыми.
- `get_video(video_id, db)` — `GET /api/videos/{id}`: одно видео и его статус.
- `start_processing(video_id, db)` — `POST /api/videos/{id}/process`. Если видео уже в очереди или
  обрабатывается, отвечает 409. Иначе создаёт `ProcessingJob`, ставит видео статус `queued`,
  сохраняет и вызывает `process_video.delay(job.id)`, который кладёт задачу в Redis. Если Redis
  недоступен (`OperationalError`), статусы становятся `error`, ответ 503. Код 202 означает
  «принято, выполнится позже».
- `get_last_job(video_id, db)` — `GET /api/videos/{id}/job`: последнее задание видео, по нему
  интерфейс показывает процент. Если заданий нет, ответ 404.
- `get_rallies(video_id, db)` — `GET /api/videos/{id}/rallies`: переводит строки `Rally` в формат
  задания (`start` и `end` вместо `start_time` и `end_time`) и возвращает `{video_id, rallies}`.

### backend/app/tasks.py — фоновая обработка

- `celery_app = Celery("volleyball", broker=REDIS_URL)` — приложение Celery, очередь задач в Redis.
  Воркер запускается командой `celery -A app.tasks worker`.
- `logger` — журнал воркера, в него пишутся ошибки.
- `process_video(job_id)` — задача, которую выполняет воркер:
  1. импортирует `detect_video` внутри функции, чтобы PyTorch и модели загружались только в воркере;
  2. открывает сессию, находит задание и его видео, ставит обоим статус `processing` и время старта;
  3. внутренняя функция `save_progress(percent)` записывает процент в базу, её вызывает
     `detect_video` после каждого пакета кадров;
  4. `detect_video` строит временной ряд, он сохраняется в файл `job_<id>_detections.json`;
  5. `find_rallies` выделяет розыгрыши;
  6. старые розыгрыши видео удаляются (`clear` и `flush`, чтобы удаление выполнилось раньше вставки
     и не сработало ограничение `UNIQUE(video_id, number)`), новые добавляются;
  7. статусы становятся `completed`, прогресс 100;
  8. при любой ошибке транзакция откатывается, статусы становятся `error`, текст ошибки
     записывается в `error_message`;
  9. в конце записывается время окончания `finished_at`.

### backend/app/detection.py — нейросети

- Константы: `SEQUENCE_LENGTH = 9` (модель мяча смотрит на 9 кадров), `INPUT_WIDTH` × `INPUT_HEIGHT`
  = 512 × 288 (размер входа модели), `PERSON_CLASS = 0` (класс «человек» в наборе COCO).
- `preprocess(frame)` переводит кадр в оттенки серого, уменьшает до 512 × 288 и делит на 255,
  чтобы яркость была от 0 до 1.
- `find_ball(heatmap, threshold, scale_x, scale_y)` находит мяч на одной тепловой карте: строит маску
  точек со значением больше 0,5, выделяет связные области (`connectedComponentsWithStats`), берёт
  самую большую, её центр считает положением мяча, а максимум карты в ней — уверенностью.
  Координаты умножаются на `scale_x` и `scale_y`, чтобы перейти к размеру исходного кадра.
  Если областей нет, `x` и `y` равны `None`.
- `BallDetector` — обёртка над VballNet:
  - `__init__(model_path, threshold)` загружает ONNX-модель в ONNX Runtime (на процессоре) и
    запоминает имя её входа;
  - `detect(frames)` готовит 9 кадров (неполный последний пакет дополняет копиями последнего кадра),
    собирает массив формы `(1, 9, 288, 512)`, запускает модель и для каждого кадра пакета вызывает
    `find_ball` по его тепловой карте.
- `PlayerDetector` — обёртка над YOLO26:
  - `__init__(model_name, confidence)` загружает `yolo26n.pt` через библиотеку `ultralytics`;
  - `detect(frames)` вызывает `model.predict` только для класса «человек» с порогом 0,3 и для
    каждого кадра возвращает список рамок `[x1, y1, x2, y2, уверенность]`.
- `read_frames(capture, count)` читает из видео до `count` кадров подряд; в конце видео возвращает
  столько, сколько осталось.
- `detect_video(video_path, ball_model_path, player_model, on_progress)` — главная функция модуля.
  Читает метаданные, создаёт оба детектора, в цикле читает пакеты по 9 кадров, отдаёт пакет обеим
  моделям и складывает записи временного ряда `{frame, ball_x, ball_y, ball_confidence, players}`.
  После каждого пакета сообщает процент (не больше 99: 100 ставит задача, когда всё сохранено).
  Возвращает `fps`, `width`, `height`, `frame_count` и список кадров `frames`.

### backend/app/rallies.py — алгоритм

- `GAME`, `NON_GAME` — метки состояния кадра.
- `RallyParams` — четыре параметра со значениями по умолчанию: `min_speed` 0,1, `max_gap` 1,0 с,
  `min_duration` 2,0 с, `merge_gap` 2,0 с. Декоратор `@dataclass` сам создаёт конструктор.
- `seconds_to_frames(seconds, fps)` переводит секунды в кадры: 1 с при 25 кадрах/с — 25 кадров.
- `format_time(seconds)` превращает 83,46 в строку `"01:23.5"` для вывода в консоли.
- `ball_speeds(frames, fps, width, max_step)` считает скорость мяча в каждом кадре в ширинах кадра
  в секунду по предыдущей детекции, если она была не дальше `max_step` кадров назад. Если мяча нет
  или предыдущей детекции нет, скорость `None`.
- `active_frames(frames, fps, width, params)` — сырая отметка: `True`, если скорость известна и не
  меньше `min_speed`.
- `fill_gaps(flags, max_gap_frames)` закрашивает провалы не длиннее `max_gap_frames` между
  активными кадрами.
- `find_segments(flags)` превращает список `True`/`False` в отрезки `(первый кадр, последний кадр)`:
  `[F, T, T, F, T]` → `[(1, 2), (4, 4)]`.
- `merge_segments(segments, merge_gap_frames)` склеивает отрезки, если пауза между ними не больше
  `merge_gap_frames`.
- `classify_frames(frames, fps, width, params)`: активные кадры → заполнение пропусков → отрезки →
  отрезки короче `min_duration` отбрасываются → метка `GAME` или `NON_GAME` для каждого кадра.
- `find_rallies(frames, fps, width, params)` — главная функция: метки → отрезки → склейка → список
  розыгрышей с номером, временем начала и конца (номер кадра, делённый на FPS, два знака после
  запятой), номерами кадров и `serve_side = "unknown"`.

Подробнее о двух ключевых функциях:

```python
# ball_speeds: previous — последний кадр, где был мяч
if previous is not None and item["frame"] - previous["frame"] <= max_step:
    seconds = (item["frame"] - previous["frame"]) / fps
    distance = math.hypot(item["ball_x"] - previous["ball_x"], item["ball_y"] - previous["ball_y"])
    speed = distance / width / seconds           # ширин кадра в секунду
```

`math.hypot(dx, dy)` — расстояние по теореме Пифагора.

```python
# fill_gaps: last_active — последний активный кадр
if last_active is not None and i - last_active - 1 <= max_gap_frames:
    for k in range(last_active + 1, i):
        result[k] = True
```

`i - last_active - 1` — сколько неактивных кадров между двумя активными. Если не больше
допустимого, они закрашиваются как игра.

### backend/alembic — миграции

- `env.py` — настройка Alembic: подключение берётся из `app.database`, список таблиц — из
  `Base.metadata`. `run_migrations_online()` выполняет миграции через подключение к базе,
  `run_migrations_offline()` печатает SQL без подключения. `render_as_batch=True` нужен для SQLite.
- `versions/0001_initial_tables.py`: `upgrade()` создаёт четыре таблицы с ограничениями и два индекса,

### backend/scripts — запуск из консоли

- `analyze_video.py`:
  - `parse_args()` читает аргументы: видео или `--detections` (готовый JSON), папку `--out`, путь
    к модели мяча и четыре параметра алгоритма;
  - `main()` берёт детекции из JSON или запускает `detect_video` и сохраняет их, затем вызывает
    `find_rallies`, записывает `<имя>_rallies.json` и печатает розыгрыши.
- `evaluate.py`:
  - `SWEEP` — значения параметров для перебора;
  - `frames_in_rallies(rallies, fps, total)` размечает кадры по интервалам: `True` внутри розыгрыша;
  - `overlap_ratio(a, b)` — IoU двух интервалов;
  - `evaluate(predicted, truth, fps, total)` считает покадровые точность, полноту и F1, сопоставляет
    розыгрыши по IoU ≥ 0,5 и считает средние ошибки начала и конца;
  - `main()` читает детекции и эталон, оценивает параметры по умолчанию, а с флагом `--sweep` —
    каждое значение из `SWEEP`; печатает таблицу и сохраняет CSV.
- `compare_ball_models.py`:
  - `load_truth(path)` читает CSV с разметкой мяча из датасета автора;
  - `vballnet_points(video, model_path)` — положения мяча от VballNet для каждого кадра;
  - `yolo_points(video, model_path, image_size)` — положения мяча от YOLO26: класс «sports ball»,
    центр самой уверенной рамки;
  - `score(points, truth, tolerance)` считает точность, полноту и F1; попадание засчитывается, если
    точка не дальше 9 пикселей от разметки при ширине кадра 1920;
  - `main()` сравнивает VballNetV4c, VballNetFastV1 и YOLO26 при входе 640 и 1280 и печатает
    таблицу со временем на кадр.

## 23. Возможные вопросы преподавателя и ответы на них

**1. Почему не обучили свою нейросеть?**
По заданию нужен минимальный уровень: отделить игру от пауз. Готовые модели уже решают
трудную часть (найти мяч и людей), а состояние игры по их выходу определяют прозрачные правила.
Обучение потребовало бы размеченного датасета и GPU.

**2. Почему мяч ищет не YOLO26?**
Мы проверили: класс «sports ball» в YOLO26n находит волейбольный мяч в 0–18 % кадров (F1 до 0,30),
VballNet — в 73–88 % (F1 0,79–0,87). Мяч слишком мелкий и смазанный для детектора общего назначения.

**3. Зачем тогда YOLO26?**
Она находит людей. Список игроков `players[]` входит во временной ряд, который требует задание ИР 4.
Алгоритм выделения розыгрышей его не использует; игроки пригодятся, например, для определения
стороны подачи (задание ИР 5).

**4. Почему VballNet получает 9 кадров, а не один?**
По одному кадру маленький размытый мяч трудно отличить от пятна. Последовательность кадров
показывает движение, и модель находит мяч увереннее. Так устроены модели семейства TrackNet.

**5. Что такое тепловая карта?**
Изображение того же размера, что вход модели, где в каждой точке число от 0 до 1 — насколько
модель уверена, что там мяч. Мы берём центр самой большой области со значением выше 0,5.

**6. Зачем делить скорость на ширину кадра?**
Чтобы порог `min_speed` работал одинаково для видео 854×480 и 1920×1080. В пикселях один и тот же
полёт мяча на разных разрешениях даёт разную скорость.

**7. Почему параметры подобраны вручную, а не обучены?**
Их четыре, у каждого есть физический смысл (секунды и скорость), и их влияние видно на графиках.
Это проще проверить и объяснить, чем обучаемую модель, и для минимального уровня задания этого достаточно.

**8. Как вы проверяли качество?**
В 8-минутном фрагменте трансляции вручную размечены 16 розыгрышей; по ним посчитаны покадровые точность,
полнота, F1 и совпадение интервалов по IoU ≥ 0,5. Детектор мяча проверен по готовой разметке мяча
из датасета автора fast-volleyball-tracking.

**9. Почему F1 всего 0,61?**
Модель мяча обучена на статичной камере, а проверка шла на телетрансляции другого ракурса
и качества 480p: мяч найден только в 35 % кадров розыгрышей. Кроме того, правило не отличает
от игры крупные планы и повторы, а также броски мяча между розыгрышами. На статичной камере
результат совпал с ожидаемым.

**10. Почему детекции не хранятся в базе?**
Их около 15 600 на минуту видео, на матч ~1,9 млн строк. Интерфейсу они не нужны, а SQLite
блокировала бы базу на время записи. JSON-файл компактнее (5,5 МБ против 9,4 МБ) и позволяет
пересчитать розыгрыши без нейросетей.

**11. Зачем Redis и Celery, если можно обработать видео прямо в запросе?**
Обработка длится минуты. HTTP-запрос оборвался бы по тайм-ауту, а сервер не мог бы отвечать
другим пользователям. Очередь отделяет приём запроса от долгой работы и позволяет показывать прогресс.

**12. Что будет, если упадёт воркер или не будет Redis?**
Без Redis API сразу вернёт 503 и пометит задание ошибкой. Ошибка внутри обработки ловится
в задаче: статусы становятся `error`, текст ошибки сохраняется и показывается в интерфейсе.

**13. Зачем таблица `users`, если входа в системе нет?**
Сущность User с полями `email` и `password_hash` требует задание ИР 1: оно про проектирование базы.
Регистрация и вход — задание ИР 2, в нашу работу оно не входит. Поэтому таблица есть в схеме и
миграции, а `videos.user_id` пока может быть пустым. Когда появится вход, структуру базы менять
не придётся.

**14. Как будут храниться пароли?**
Только в виде хеша в поле `password_hash`, например PBKDF2 или bcrypt с солью. Сам пароль в базу
не записывается: при утечке базы по хешу его не восстановить.

**15. Зачем Alembic, если таблицы можно создать через `create_all`?**
`create_all` только создаёт отсутствующие таблицы и не умеет изменять существующие.
Миграции фиксируют историю схемы и меняют её без потери данных.

**16. Что такое `serve_side` и почему он `unknown`?**
Сторона подачи (ближняя `near` или дальняя `far`). Это бонусная задача задания ИР 5;
поле есть в схеме, чтобы потом не менять базу.

**17. Как работает `max_gap` и чем он отличается от `merge_gap`?**
`max_gap` заполняет короткие провалы до удаления коротких фрагментов: склеивает куски одного
розыгрыша, разорванные потерей мяча на доли секунды. `merge_gap` работает после удаления коротких
и склеивает уже надёжные сегменты. Если поменять шаги местами, F1 падает с 0,609 до 0,542.

**18. Как вы проверяли, что программа работает?**
Запуском на реальных видео. Качество алгоритма посчитано по эталонной разметке трансляции
(`scripts/evaluate.py`). Вся система прогнана в Docker: загрузка ролика через API и через страницу
в браузере, обработка воркером, получение розыгрышей; проверены и ответы на ошибочные запросы
(400, 404, 409).

**19. Почему на роликах со статичной камерой результат лучше?**
VballNet обучена именно на таких записях: камера за лицевой линией, без монтажа. На трёх таких
роликах алгоритм выделил по одному интервалу, который покрывает игру почти целиком.

**20. Сколько времени занимает обработка?**
На процессоре Apple M1 Pro видео 1920×1080 длиной 33 с обрабатывается за 49 с, а видео 854×480
длиной 7 мин 56 с — за 7 мин 42 с. В Docker Desktop тот же 33-секундный ролик обрабатывался 5 мин 48 с:
внутри виртуальной машины Docker нейросети работают в 2,5–3 раза медленнее.
Основное время занимает YOLO26.

**21. Как улучшить результат?**
Дообучить VballNet на трансляциях; добавить разметку площадки и проверять, что мяч над ней;
учитывать число игроков в кадре, чтобы отсекать крупные планы (на трансляции условие «не меньше
6 человек» поднимало F1 до 0,67, но в итоговую версию не вошло ради простоты); обучить простой
классификатор по признакам траектории; запускать YOLO26 не на каждом кадре, чтобы ускорить обработку.

**22. Можно ли перейти на PostgreSQL?**
Да. Код работает через SQLAlchemy, достаточно поменять `DATABASE_URL` и убрать параметр
`check_same_thread`, нужный только SQLite.
